## 2. Ключевые тезисы участников

**ГД.** В КП обещаны три вещи: прозрачный план/факт, объяснённые отклонения, быстрый расчёт и ТКП. Сейчас главный риск — доверие к данным. Если перенос плана стирает просрочку, система «врёт» руководителю, и это хуже, чем Excel. Задача итерации — закрыть дыры доверия и коммерции, а не расширять продукт. Бюджет 350 000 ₽ фиксирован, лишний объём оплачивать некому.

**ДП.** В цехе спрашивают одно: когда отдадим заказчику. Ответ «сдача через 21 день» у заказа с просроченным этапом в пилоте опасен. Плановые даты молча двигать нельзя: план — это обязательство. Нужен прогноз рядом с планом. Факт часто вносят задним числом, не «сегодня». Отметки из будущего надо запретить.

**ТД.** По коду: подтверждаю п. 1, 2, 5, 6, 7, 10, 16 полностью, частично ложные тревоги — п. 7, 10, 17 (подробности в разделе 3). Схема одна на сервер и демо: `openDb()` в `src/db.js` выполняется и в node:sqlite, и в sql.js через `demo/shims/sqlite.js`. Значит, любая миграция — только чистый SQL плюс проверки `PRAGMA table_info` / `sqlite_master`, без файловых операций. CHECK на роли в SQLite нельзя изменить через ALTER, нужна пересборка таблицы `users`. Это делается за час и работает в sql.js. Предлагаю убрать CHECK совсем и проверять роль по `ROLES` в приложении: `refs.js` уже это делает. Тогда следующие роли миграций не потребуют.

**ФД.** НДС 20% зашит в четырёх местах, с 01.01.2026 ставка 22% — ТКП с 20% отправлять нельзя. Документ ТКП должен иметь фиксированную дату, срок действия и условия оплаты, иначе юридически это черновик. Деньги в проекте нужны минимально: сумма привязанного расчёта и «сумма под угрозой» в отчёте. Маржа и скидки — после калибровки ставок на реальных заказах (КП, п. 6).

**КД.** Для продаж следующим клиентам решают демо-сценарии: «перенос плана с причиной и журналом», «прогноз сдачи», «ТКП с реквизитами и НДС 22%». Это видно за 3 минуты показа. Экспорт в Excel спрашивают все, но на демо он не продаёт, его можно сделать следом.

**ДПр.** Оценки 5,1–5,5 во всех группах — повод для работы, а не провал. Ядро (доска, обязательный комментарий, маршрут) все поняли за 10 секунд. Минимальный пакет для телефона дешёвый: плашка «Сохранить» только при правках, цели 44 px, текст не мельче 13 px. Полная мобильная вёрстка таблицы этапов стоит дороже, её — в следующий этап. Доступность: подписи полей и skip-link — час работы, а блокер для пользователя экранного диктора реальный.

**ПК.** Ждём ровно то, что в КП: четыре роли, почта, план/факт с комментарием, калькулятор в тестовом режиме, ТКП. Мобильный доступ цеха в КП вынесен за рамки первого этапа. Против того, чтобы цикл доработки сам сдвигал договорной срок: срок перед заказчиком меняет человек. Роль мастера не просили, но не возражаем, если это не стоит денег и не ломает четыре роли. Безопасность входа и бэкап обязательны до запуска на реальных заказах.

### 4.3. «НЕ ДЕЛАЕМ»

| Что | Причина |
|---|---|
| Интеграция и обмен с 1С, бухгалтерский учёт, счета | КП: система «не пересекается с бухгалтерским учётом», 1С не меняем |
| Контур ГОЗ, разграничение данных по ГОЗ | КП: пилот только на гражданском направлении; ГОЗ — после пилота отдельным решением |
| Автоматический сдвиг плановых дат следующих этапов при опоздании | Противоречит принципу «отклонение всегда видно»: план — обязательство, сдвиг стирает просрочку. Вместо этого прогноз (п. 3) и перенос плана с причиной (п. 2) |
| Загрузка сотрудников, аналитика производительности | КП, п. 3.3: обсуждается отдельно, данных для этого пока нет |
| Диаграммы Ганта и сложные графики с перетаскиванием | КП, п. 3.3: «без сложных графиков»; позиционирование — диспетчерская доска, не ERP |
| Складской учёт, закупки, снабжение как модуль | Вне задачи «контроль производства и расчёт КП», позиционирование против «большой ERP» |
| Нативное мобильное приложение | КП: «ничего не нужно скачивать и устанавливать»; веб-доступ с телефона закрывается адаптивом |

## 5. Роль «Мастер/исполнитель»: как добавить минимальными изменениями (заключение ТД)

1. **Права.** `src/auth.js`: `ROLES.master = 'Мастер / исполнитель'`, `PERMS.master = []`. Новых проверок не нужно: в `PUT /api/projects/:id/stages` пользователь без `stage.edit` может править только этапы, где `responsible_id = req.user.id`, и только `fact_date`/`comment`. Попытка поменять `plan_date` или `responsible_id` → 403. Клиент (`views/project.js`) уже показывает таким пользователям план текстом, а факт — полем ввода только для своих этапов.
2. **Схема.** Для новых БД — убрать CHECK из `users.role` (или расширить список). Для существующих БД миграция в `openDb()`:
   - условие: `SELECT sql FROM sqlite_master WHERE name='users'` содержит `CHECK (role IN` без `'master'`;
   - `PRAGMA foreign_keys=OFF` → `BEGIN` → `CREATE TABLE users_new (…без CHECK…)` → `INSERT INTO users_new SELECT id, login, name, email, role, pass_hash, active FROM users` → `DROP TABLE users` → `ALTER TABLE users_new RENAME TO users` → `COMMIT` → `PRAGMA foreign_keys=ON` (+ `PRAGMA foreign_key_check` в тесте).
   - Внешние ключи `sessions`, `projects`, `project_stages`, `stage_comments`, `estimates` ссылаются на таблицу по имени `users` и после переименования снова разрешаются. Сессии сохраняются, потому что каскад при выключенных FK не срабатывает.
   - Всё — чистый SQL, работает в sql.js (демо).
3. **Уведомления.** Ничего не меняем: `recipientsFor` уже берёт ответственного за этап.
4. **UI.** Список ролей в справочнике пользователей строится из `refs.roles` — новая роль появится сама. Выпадающий список ответственных показывает всех активных пользователей. Фильтр «Мои» (п. 7) — основной экран мастера.
5. **Чего не делаем:** отдельный интерфейс цеха, права по участкам, роли ОТК и снабжения.

Трудоёмкость — M (2 ч с тестами).

## 7. Итоговое поручение разработке (порядок выполнения)

Срок — одна итерация (~2 рабочих дня). После каждого пункта: `npm test`; в конце — `npm run build:demo`, проверка демо (375 px и 1280 px, роли `prod`, `tech`, `sales`, мастер), обновление `PROGRESS.md`.

2. **НДС 22% по умолчанию** — константа, схема, калькулятор, сиды (S).
3. **Базовый план, причина переноса, журнал изменений, запрет безвозвратного удаления проекта** (L).
